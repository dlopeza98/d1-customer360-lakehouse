El mismo código en Azure y en GCP

Cómo está armado el POC para que moverlo de una nube a la otra sea un cambio de configuración y no una reescritura.

La pregunta no es cuánto tardamos en copiar. Es qué parte del sistema sabe en qué nube está. Si esa parte es grande, migrar es reescribir. Si es pequeña y está aislada, migrar es reprovisionar.

En este proyecto esa parte son dos líneas, y las dos están en databricks.yml. Las 488 líneas de lógica — notebooks, definición del job, reglas de identidad — no mencionan una nube ni una vez.

Por qué el código no necesita saber dónde corre

Los notebooks nunca escriben una ruta de almacenamiento. Direccionan las tablas por nombre de tres niveles — catálogo.esquema.tabla — y Unity Catalog resuelve dónde vive físicamente cada una: en Azure apunta a ADLS Gen2, en GCP a Cloud Storage.

Esa indirección es lo que hace posible todo lo demás. Sin ella, cada notebook tendría una ruta escrita a mano y migrar sería reescribir.

El demo, en tres movimientos

1

Medir cuánto del sistema conoce la nube

No lo afirmes: muéstralo. El resultado es el argumento entero.

bash scripts/verificar_portabilidad.sh

  OK: 0 referencias de nube en 4 archivos / 488 líneas.
  2 líneas conocen la nube. Son declaraciones, no lógica.
2

Abrir un notebook y buscar una ruta

Busca abfss delante de ellos. Cero resultados. Después abre databricks.yml: dos targets, un host cada uno. Eso es todo lo que separa una nube de la otra.

3

Desplegar en la otra nube

El mismo comando, distinto target. Se redespliega el job completo sin editar un solo notebook. 

databricks bundle deploy -t azure
databricks bundle deploy -t gcp

El detalle que atrapa a quien porta esta infraestructura

En Azure tú creas la identidad administrada y le pasas su id a Databricks. En GCP Databricks genera la service account y tú le asignas los roles IAM sobre los buckets. La flecha apunta al revés.

Portar la infraestructura con el modelo mental de Azure produce un resultado que parece correcto y no lo es: una identidad con permisos que Databricks no usa, y una identidad sin permisos que sí usa. Vale la pena mencionarlo — es el tipo de detalle que un equipo de infraestructura reconoce al vuelo.

Alcance

El aprovisionamiento del POC es manual y documentado. La propuesta excluye explícitamente Infraestructura como Código y pipeline de CI/CD: son alcance de proyecto, no de POC. Lo que se entrega es el repositorio versionado en GitHub.
